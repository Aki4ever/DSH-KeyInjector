## 1. 目标与执行偏差反思 (Variance Analysis)

### 初始规划 vs 实际执行

| 阶段 | 原计划 | 实际执行 | 偏差评价 |
| :--- | :--- | :--- | :--- |
| 需求确认 | 直接按「注入器」字面开工 | 先三问澄清语义/形态/建仓，锁定唯一目标 | ✅ 收敛，避免了最贵的方向性返工 |
| 核心技术栈 | SwiftUI 桌面应用 | **被迫改为 AppKit + WKWebView + 原生前端** | ⚠️ 最大偏差，属环境硬约束（见第 2 节） |
| 测试框架 | XCTest | **被迫改为 swift-testing** | ⚠️ 环境硬约束 |
| 页面台账 | `screencapture` 截图 | **被迫改为应用内 `WKWebView.takeSnapshot`** | ✅ 偏差反而带来更优方案 |
| 界面层返工 | — | SwiftUI 层写完后整体废弃重写 | ❌ 若**先做技术栈可行性探测**，可完全避免 |

**最大的可避免浪费**：先按惯性用 SwiftUI 写完整个界面层（1 个入口 + 1 个视图模型 + 6 个视图文件），
再撞上「本机 CLT 缺 `SwiftUIMacros`，SwiftUI 根本无法编译」的硬墙，导致该层全部作废重写。

> **根因**：把「Swift 项目就用 SwiftUI」当成**常识假设**，而没有把「技术栈在本机是否可编译」
> 当作**动手前必须验证的前置事实**。这与元规则「前置风险揭示」的精神相悖——
> 风险揭示不应只针对破坏性操作，也应针对**技术可行性**。

### 意图收敛效率

需求分析一步到位：三轮澄清后未再发生目标漂移，全程围绕「本机密钥管理 + 安全注入 + 桌面交付」推进，

## 2. 实战踩坑与根因剖析 (Root Cause & Lessons)

### 坑 1：本机 Swift 工具链缺 SwiftUI 与 XCTest 两套宏/框架

- **现象**：`SwiftUIMacros … plugin not found`（每个 `@State`/`@Binding` 一处报错）；
  `unable to resolve module dependency: 'XCTest'`。
- **底层根因**：本机仅装 Command Line Tools；该工具链的 `host/plugins/` 下只有
  `libObservationMacros.dylib`、`libSwiftMacros.dylib` 与 `testing/`，**不存在 SwiftUIMacros**，
  而此 SDK 中 SwiftUI 的 `@State` 等已改为宏实现 → SwiftUI 在此环境下**物理上无法编译**。
  XCTest 亦未随附，但 swift-testing 随附可用。
- **认知升级**：**「Swift 能用」不等于「SwiftUI 能用」**。技术栈可行性必须在写第一行代码前用一次最小
  编译探针验证，而不是靠经验假设。本次在发现后立即用 AppKit + WebKit 探针（NSWindow + WKWebView
  程序化创建）验证可行，才动手重写——这一步做对了，但**做得太晚**。

### 坑 2：SPM 增量编译漏传测试宏插件路径

- **现象**：首次 `swift test` 全绿，第二次起突然 96 处 `TestingMacros … not found`。
- **底层根因**：SPM 在**增量** emit-module 步骤未自动附加 `-plugin-path`（全新构建反而正常）。
  这一「首次正常、二次报错」的形态极易被误判为代码问题，从而浪费时间排查源码。
- **对策**：门禁脚本显式传入 `-Xswiftc -plugin-path -Xswiftc "$PLUGIN_DIR"`，
  且 `$PLUGIN_DIR` 由 `xcrun --find swift-frontend` 动态推导，不硬编码。

### 坑 3：`screencapture` 被 TCC 隐私门禁拒绝

- **现象**：全屏截图报 `could not create image from display`，区域截图报 `could not create image from rect`。
- **底层根因**：macOS 屏幕录制 TCC 授权未授予本进程。**两种报错文案不同**，区域报错极易被误判为
  「坐标算错了」，从而反复调整窗口位置与取景参数——这是典型的**错误归因陷阱**。
- **对策**：识别为权限问题而非几何问题；页面台账改用应用内 `WKWebView.takeSnapshot`
  （无需系统权限、只含页面内容、出图可复现）。

### 坑 4：备份文件名秒级时间戳导致同秒连续备份互相覆盖

- **现象**：注入偶发失败，报 `NSCocoaErrorDomain Code=516 文件已存在`。
- **底层根因**：**真实生产缺陷**——备份文件名用秒级时间戳，同一秒内两次备份同名冲突。
  该缺陷由自己编写的测试用例暴露（「同秒内连续备份不互相覆盖」）。
- **对策**：改为毫秒级时间戳 `yyyyMMdd-HHmmss-SSS` + 冲突自增后缀，并保留回归测试。
- **正面意义**：这次是**测试驱动发现真实缺陷**的典型案例，验证了「自动化测试不是形式主义」。

### 坑 5：自身工具调用纪律问题（无效调用）

- 3 次 `edit` 因**未先 `read`** 被文件策略拒绝 → 违反「先 read 再 edit」铁律；
- 2 次 `edit` 因文件 mtime 被 `chmod` 变更而要求重读；
- 1 次超长命令被中断，结果状态未知，需额外一轮核查（好在无中间态污染，可安全重跑）；
- 早期用 `| head -20` 截断构建日志触发 SIGPIPE，造成一次**假失败**误判。

### 坑 6：dry-run 演示险些误读用户真实配置

- **现象**：验证打包应用时未指定演示目标文件，dry-run 计划回退到落点默认路径，读到了用户**真实的** `~/.zshrc`。
- **根因**：演示脚本未强制注入"演示目标文件"变量，依赖了应用的默认值。
- **处置**：立即核查 `~/.zshrc`（mtime 保持 `Jul 15`）与 `~/.codex/auth.json`（无注入痕迹），
  确认**只读未写**。虽是只读且无损害，但**演示环境必须强制隔离，不能依赖默认值兜底**。

## 3. 体系与流程进化建议 (Evolution Suggestions)

### 规则/SOP 优化点

**建议 A（高价值）：在「探境」阶段增设《技术栈可行性探针》强制步骤**

现状：元规则的「前置风险揭示」侧重**破坏性操作**（改文件、删数据），对**技术可行性**缺少强制门禁。
本次最大浪费（整层界面返工）恰恰来自技术栈不可行，而非破坏性操作。

建议：凡引入新框架/新语言特性/新构建链，动手前必须执行**最小可编译探针**并留存回执：

```
1. 语言与框架：写 5~10 行最小可编译样本，真实执行编译/运行，贴出退出码；
2. 测试框架：确认可用测试库（本机是 swift-testing 而非 XCTest）；
3. 图形/媒体能力：确认截图、渲染、编码等系统能力是否被 TCC 隐私门禁拦截；
4. 结论写入《前置风险评估卡》，未通过则立即改道，绝不先写主体再验证。
```

**建议 B：收尾门禁增加《文档读回自检》**

本次 M4 写后读回覆盖率仅 `75%`，短板集中在**纯文档**（README、需求台账、架构说明只做了关键词 grep 校验，
未逐字读回）。文档同样会出错（错别字、命令与实现对不上、表格数字与实测不符），
而文档恰恰是用户最先看到的部分。

建议：收尾自检清单增加一项——
**「文档中出现的每条命令、每个路径、每个数字，都必须经一次真实执行或真实读取核对」**。
本次已按此自查：README 中 CLI 选项逐条对照 `--help` 实测修正，台账中的字节数与哈希全部由 `stat`/`shasum` 实测填入。

**建议 C：修正分类编号字母表缺失**

元规则与经验库多处使用 `[R/F/D/S/O/Q]` 单字母分类编号（如经验第 4 条「分类编号规范使用单字母（R/F/D/S/O/Q）」），
但**全局规则中从未定义这六个字母各代表什么类别**，新任务只能靠推测。
本次依据「development」推断使用 `D`，若与既定语义不符则标题分类有误。

建议：在 `rules/system/meta_rules.md` 或命名规范文档中**显式补上字母定义表**。
