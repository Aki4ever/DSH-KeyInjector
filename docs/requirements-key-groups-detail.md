# 密钥库「名字分区 + 模型识别 + 详情页」需求确认稿

> 文档编号：`R54`　|　状态：**待用户确认后实施**　|　目标版本：`v1.6.0`
> 来源：用户 2026-09-22 反馈（附两张界面截图）
> 主题：密钥库按 key 别名分区；每把 key 可识别「能提供哪些模型」；点击进详情

---

## 一、原始诉求还原

| 用户原话 | 真实意图（去歧义后） |
| :--- | :--- |
| 「密钥库里现在有 2 个 key，帮我在这里做好分区」 | 密钥库不再是一条条平铺的卡片，而是**先分区、再列内容** |
| 「要根据 key 的名称进行名字分区」 | 分区标题 = key 的别名（`label`），一把 key 一个分区 |
| 「名字分区下列出该 key 可以获取的模型类型」 | 分区下直接列出**这把 key 能提供的模型**，无需切页 |
| 「密钥库这边可以识别出 key 有什么模型可以提供」 | 模型来源不能只靠宿主配置，要能**从 key 自身端点识别** |
| 「点进 key 进去可以查看详情」 | 每把 key 有独立详情视图，承载完整元数据 + 完整模型列表 |

## 二、需求条目

### REQ-019 · 密钥库按 key 别名分区

| 项 | 内容 |
| :--- | :--- |
| **目标版本** | v1.6.0 |
| **需求描述** | 密钥库顶部按 key 别名（`label`）分组，一把 key 一个分区；分区标题行可折叠，分区内列出该 key 提供的模型；保留既有卡片操作（编辑 / 探测 / 启用 / 删除） |
| **交互规则** | ① 分区标题：别名 + 厂商 chip + 状态点 + 「模型 N 个」计数 + 折叠箭头；② 分区默认展开，折叠状态在会话内记忆；③ 分区排序：先「已启用」后「已禁用」，同组内按 `priority` 升序、再按别名；④ 分区内保留原有单卡布局与「供给模型」区块（本需求不删除既有能力，只做归组）；⑤ 顶部提供搜索框（按别名 / 厂商 / 模型名 / 端点匹配）与「仅看未探测/异常」筛选 |
| **验收断言** | ① 当前 2 把 key 渲染为 2 个分区；② 折叠/展开不触发网络请求、不丢失滚动位置；③ 搜索「gemini」只剩对应分区，且分区标题计数同步变化；④ 空库时仍显示原有空状态引导 |
| **不做** | 不引入拖拽排序分区；不做自定义分组（那是标签体系，属另一需求） |

### REQ-020 · 从 key 自身端点识别可用模型（多级兜底）

| 项 | 内容 |
| :--- | :--- |
| **目标版本** | v1.6.0 |
| **需求描述** | 每把 key 除「宿主配置映射」外，还能**从该 key 自己的端点拉取可用模型列表**；拉取失败时按固定顺序逐级兜底，并**如实标注来源与置信度**，绝不编造 |
| **探测优先级** | **T1 端点探测**：`GET {baseURL}{probePath}/models`，`probePath` 优先取该 key 自定义 `baseURL`（公司AI综合：`http://192.168.1.200:8080/v1`），否则取厂商预设 `baseURL` |
| | **T2 端点变体**：T1 失败（404 / 非 JSON / 超时）时依次尝试 `{baseURL}/models`、`{baseURL}/v1/models`、厂商 `healthPath` 指向的路径 |
| | **T3 响应解析**：兼容 OpenAI `{"data":[{"id":...}]}`、Gemini `{"models":[{"name":"models/xxx"}]}`、Ollama `{"models":[{"name":"xxx"}]}`、以及裸数组 `[...]` 四种形态；解析出 `id`/`name` 并剥离 `models/` 前缀与命名空间前缀 |
| | **T4 宿主映射兜底**：探测全部失败时，回退到现有 `HostModelInventory.bindings`（按凭据键名 / 端点同源匹配，即 v1.4.0 的 `modelBindings`） |
| | **T5 名称推断兜底**（你要求的「其他映射方案」）：把宿主菜单里出现、但这把 key 未声明的模型，按 `ModelIdentity.normalize` 与已知厂商目录做名称相似度比对，只做**候选提示**，置信度标为「推断」，永远不自动写入任何宿主配置 |
| **无探测端点时的方案** | 若厂商预设无 `baseURL` / `healthPath`（如 `custom` 厂商），且用户未填自定义端点：① 显示「无法探测：未配置端点」并提供一键跳转编辑；② 仍展示 T4/T5 结果并标注来源；③ 提供「手动补充模型」入口（仅写入本工具缓存，不写宿主配置） |
| **验收断言** | ① 公司AI综合 key 探测 `…/v1/models` 成功后，分区内模型数 ≥ 宿主映射的 6 个，且来源标注为「端点探测」；② 断网或 404 时来源自动降级为「宿主映射」并显示失败原因，不显示空列表；③ 四种响应形态各有单元测试（含畸形 JSON 不崩溃）；④ 探测为**显式动作**（点按钮或 CLI），不做后台轮询；⑤ 不写任何宿主配置文件 |
| **反例保护** | 密钥明文只在内存中使用，探测请求不经任何第三方；日志与缓存文件只存掩码、指纹与模型名，绝不落盘明文；上游响应正文只截断保留 200 字符用于报错说明 |

### REQ-021 · key 详情视图

| 项 | 内容 |
| :--- | :--- |
| **目标版本** | v1.6.0 |
| **需求描述** | 点击密钥卡（或分区标题）进入该 key 的详情视图，看到完整信息与完整可用模型列表 |
| **信息架构** | ① **身份**：别名、厂商、端点、掩码、指纹、优先级、标签、备注、启用状态；② **健康**：最近探测状态 / HTTP 码 / 延迟 / 探测时间 / 错误消息 + 「重新探测」按钮；③ **模型**：可用模型全量列表（模型 ID、显示名、来源标签 T1–T5、置信度、绑定凭据键名、是否在宿主菜单可见），支持按宿主/来源筛选；④ **落点**：这把 key 当前被注入到哪些宿主落点（键名、目标文件、最近注入时间）；⑤ **时间线**：创建 / 更新时间与相关审计记录（该 key 的最近 N 条） |
| **交互规则** | 详情以全屏模态呈现，`Esc` 与返回按钮均可关闭；模型列表较长时内部滚动；每行可一键复制模型 ID |
| **验收断言** | ① 密钥库任一 key 均可进入详情，且详情内模型数与分区摘要一致；② 详情内「重新探测」完成后列表与状态同步刷新；③ 关闭详情回到原滚动位置 |
| **不做** | 详情页内不允许直接改宿主配置（写入仍收敛到「注入中心」与「模型清单」的管理区） |

### REQ-022 · 缓存、CLI 与兼容

| 项 | 内容 |
| :--- | :--- |
| **缓存落盘** | 探测结果单独存于应用支持目录的 `model-cache.json`（键为 key id，值为 `{fingerprint, source, fetchedAt, httpStatus, models[]}`）；`KeyRecord` 新增字段仍为**不落盘的派生字段**，`vault.json` 结构零变更、旧文件仍可解码 |
| **新 CLI** | `keyinject key show <id> [--json]`（元数据 + 模型 + 落点 + 审计摘要）；`keyinject models probe <id|--all> [--json]`（执行 T1–T5 并输出来源与耗时）；`keyinject keys --grouped [--json]`（按别名分区输出） |
| **界面入口** | 密钥库分区标题右侧「⟳ 探测模型」；页头「全部探测模型」；key 详情内「重新探测」 |
| **验收断言** | ① 三个 CLI 子命令 `--json` 输出稳定可被脚本消费；② 缓存文件不含明文（grep 明文必为空）；③ 旧 `vault.json` 无需迁移；④ `scripts/check_version_sync.sh` 与 `scripts/run_tests.sh` 通过，测试数只增不减 |

## 三、明确不做的事（本轮新增）

| 编号 | 事项 | 为何不做 |
| :--- | :--- | :--- |
| NOT-007 | 依据探测结果自动改写 DSH `settings.yaml` 或 Codex 模型目录 | 沿用 REQ-018 的只读边界与 NOT-006；自动增删他人配置会破坏用户既有设置 |
| NOT-008 | 后台定时轮询各 key 的 `/models` | 与本工具「只在用户显式触发时联网」的既定边界冲突（NOT-003），且网关侧可能计费或限流 |
| NOT-009 | 内置硬编码的模型名单 | 与 REQ-018「模型清单以网关为唯一事实源」直接冲突；本轮模型一律来自端点探测或宿主声明 |
| NOT-010 | 把推断结果（T5）当作事实展示 | 推断可能出错，必须以「推断」标签降权显示，避免用户误信 |
