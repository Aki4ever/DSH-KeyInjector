## 二、各页说明

### P-001 · 密钥库（默认，名字分区）

- **入口**：应用启动后的默认页 / 侧边栏「密钥库」
- **页面元素**：顶部工具区（搜索框、仅看未探测/异常、全部折叠、全部识别模型、全部探测、新增密钥）；**按 key 别名分区的可折叠列表**；分区标题行（折叠箭头、状态点、别名、厂商 chip、模型计数、详情 / 识别模型按钮）；分区内每张密钥卡（掩码、指纹、端点、探测状态、更新时间和右侧操作区）
- **本图要点**：实机 2 把 key 渲染为 2 个分区——`Gemini( tftiphone@gmail.com )` 与 `公司AI综合`；侧边栏计数徽标显示 2 把密钥；掩码默认不暴露明文

### P-002 · 密钥库（分区内模型已展开）

- **入口**：密钥库 → 分区内「可提供模型 N 个」标题行
- **页面元素**：模型区块按来源分组（端点探测 / 宿主映射 / 推断 / 未知），每行含来源标签、置信度词、宿主标签、凭据键名、依据说明与复制按钮
- **本图要点**：`公司AI综合` 分区展开后列出 6 个模型身份，全部标注来源「宿主映射」+ 置信度「宿主声明」+ **依据「凭据键名 MIDPRO_API_KEY 且端点同源」**——依据与来源对用户可见，不做「看起来像事实」的裸列表

### P-003 · 密钥库（key 详情弹窗）

- **入口**：密钥卡标题、或卡片/分区标题右侧「详情」
- **页面元素**：全屏模态，五段信息架构——身份（别名、厂商、端点、掩码、指纹、优先级、启用状态、标签、备注、创建/更新时间）、健康探测（状态、HTTP、延迟、探测时间、消息）、可提供的模型（来源标签 + 全量列表 + 每行依据）、注入落点、最近审计记录；底部「改为探测鉴权」「重新探测模型」「关闭」
- **本图要点**：详情内模型数与分区摘要一致（同为 6 个）；健康探测段显式标注「只代表此刻鉴权是否通过，不代表额度与模型可用性」，避免误读

### P-004 · 密钥库（新增密钥弹窗）

- **入口**：密钥库 → 右上角「＋ 新增密钥」
- **页面元素**：厂商下拉；厂商信息卡（环境变量名、API 基址、申请入口、「打开」按钮、探测方式说明与反例提示）；别名、API 基址/代理端点、密钥明文（带眼睛切换）、优先级、标签、备注；底部安全提示
- **本图要点**：厂商信息卡随所选厂商实时切换，把「该厂商用哪个环境变量、去哪申请」直接呈现在录入现场

### P-005 · 模型清单（跨宿主清单 + 网关事实源）

- **入口**：侧边栏「模型清单」
- **页面元素**：**清单从哪来**（DSH settings.yaml 与 Codex 目录路径、声明条数、凭据配置数、默认模型、供应商、路由体检）；**网关事实源**（配置文件、上游基址、线路表 route→upstreamModel、同步计划、同步按钮）；**条目明细**（按归一化身份聚合的模型，逐条列出各宿主声明、凭据键名、来源文件与端点）；**Codex 模型目录管理**（新增/隐藏/删除网关条目、显示官方条目开关）；右上搜索框

### P-006 · 注入中心（dry-run 计划已生成）

- **入口**：侧边栏「注入中心」→ 生成计划
- **页面元素**：一键注入生效卡；落点选择（DSH 桌面端凭据 YAML / Codex 独立 Profile TOML）；第三步核对区（落点、写入路径、文件状态、注入键名、使用密钥与指纹、差异提示、确认写入/放弃）；回滚：最近注入记录

### P-007 · 健康探测（默认）

- **入口**：侧边栏「健康探测」
- **页面元素**：四类统计卡（有效 / 无效 / 额度限流 / 未探测）；逐项探测列表（状态色点、别名、厂商、探测状态、耗时、探测时间、说明、探测按钮）
- **本图要点**：未做真实探测时统计如实显示「未探测」，不伪造结果

### P-008 · 审计日志（默认）

- **入口**：侧边栏「审计日志」
- **页面元素**：筛选标签（全部 / 注入 / 回滚 / 密钥变更 / 探测 / **模型发现**）、刷新按钮；时间线列表（动作名、时间戳、说明、目标文件、备份路径、回滚按钮）
- **本图要点**：v1.6.0 新增「模型发现」动作类型；注入记录中**只出现掩码**，验证审计不含明文

- **入口**：侧边栏「设置与说明」
- **页面元素**：数据位置（数据目录、密钥后端、审计文件、厂商/落点数量）；配置模板；安全等级与边界（含全部反例）；命令行基座用法示例

## 三、截图生成方式

本项目的页面台账并非用系统 `screencapture` 截取，而是由应用自身的 **WKWebView 渲染快照**产生：

```bash
cd "/Users/linqiyu/Documents/DSH/注入器以及key管理工具"
rm -rf /tmp/ki-snap && bash scripts/build_app.sh
KEYINJECTOR_SNAPSHOT_DIR=/tmp/ki-snap "dist/Key注入器.app/Contents/MacOS/KeyInjector"
# 捕获完成后逐一查看 /tmp/ki-snap/*.png，确认无误再复制到 docs/screenshots/
```

**为什么不用 `screencapture`**：本机未授予终端屏幕录制权限，实测两者均失败
（`could not create image from display` / `could not create image from rect`）。
改用应用内快照后有三个额外好处：① 不需要系统权限；② 只包含页面内容，无桌面干扰；
③ 窗口尺寸可固定，出图可复现。

**步骤顺序**（`AppDelegate.runSnapshotHarness`）：密钥库默认 → 分区模型展开 → key 详情 → 新增密钥弹窗
→ 模型清单 → 注入中心 dry-run → 健康探测 → 审计日志 → 设置与说明。

**排障要点（实测踩坑，务必保留）**：快照脚本的每一步都会把执行异常写进 stderr
（`STEP_ERR <步骤名>: …`）。v1.6.0 开发期正是因为**先补齐了这个日志**，才定位到两处真实缺陷：
① 详情弹窗的 DOM 写在 `<script src="app.js">` 之后，导致 `$('#detail-close')` 为 null、
顶层脚本直接抛错、整页白屏；② 曾经用一个顶层 `try { … }` 包裹整个 `app.js` 做异常自曝，
结果把全部 `const`/`let` 关进了块级作用域，`window.state`、`call` 等全部消失。
两条都只在浏览器里复现、在 `jsc` 语法检查里完全看不出来。
